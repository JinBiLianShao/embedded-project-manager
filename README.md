# 嵌入式开发项目管理系统

> 一个给嵌入式工程师自己用的项目档案柜。
> 每个固件版本对应一份二进制、一份配置、一串 MD5，还有它被谁在什么时候测过、结果如何。
> 时间久了回头查「这块板子当时烧的到底是哪版固件」，能一秒翻出来。

作者：连思鑫 · © 2026 南京仙容信息科技有限公司 · MIT License

## 写在前面

这个项目最早是我自己用的。做嵌入式这些年，最烦的两件事：

1. **固件版本对不上**。客户说「上次那版有问题」，我得翻硬盘、翻微信、翻邮件，找出 `test_final_v3_真的最终版.bin` 到底对应哪次改动。
2. **测试记录散落各处**。谁测的、哪天测的、当时测的是哪个版本、失败原因是什么——全在聊天记录里，过两周就找不到了。

所以我写了这个工具，把它当成一个**只干这两件事、但要把这两件事做扎实**的小软件。不联网、不上云、数据就在本地一个 JSON 文件里，随时能拷走。

v1.x 是我边用边堆出来的，功能能用但结构很乱：一个 1595 行的 `renderer.js`，全靠浏览器里实时跑 Babel 编译，加个功能越来越难受。v2.0 我把它整个重写了一遍——不是重写界面，是重写**骨架**，顺手把用下来发现的那些坑全填了。

## v2.0 改了什么

### 架构：从单文件到分模块

v1.x 的样子：

```
main.js          356 行   主进程
preload.js        21 行
renderer.js     1595 行   所有界面塞在一个文件里
babel.min.js     3.1 MB   运行时编译 JSX
react.production.min.js   React 直接放仓库根目录
```

每次启动，Chromium 要先加载 3MB 的 Babel，再把 1595 行 JSX 现场编译一遍才出界面。改一行代码要重启整个应用。

v2.0 改成：

```
src/main/        主进程，按职责拆成 5 个模块
src/preload/     contextBridge 桥接层
src/renderer/    React 渲染层，按组件/hooks/utils 分目录
build/           esbuild 打包脚本
```

用 esbuild 预编译，产物 `bundle.js` 只有 **205 KB**。启动不再现场编译，改代码有 `--watch` 模式自动重建。

### 修掉的实际问题

这些不是我拍脑袋想的，是重构时逐行核对代码找出来的：

| 问题 | v1.x 的表现 | v2.0 的处理 |
|---|---|---|
| 测试记录不能编辑 | 只能新增和删除，打错字只能删了重录 | 补上编辑入口，字段全部可改 |
| 测试记录不关联版本 | 只记「谁哪天测的」，不知道测的哪版 | 加 `versionId` 字段，列表里明确标注 |
| 点选日期新增却落在今天 | 日历上点 10 号，新增的记录日期是今天 | 弹窗接收选中日期（实测点 20 号 → 默认 2026-11-20） |
| 日期时区偏移 | `new Date('2026-11-03')` 按 UTC 解析，UTC 以西的时区会退一天 | 手工拆解年月日，绝不把裸日期交给 `Date` 构造函数 |
| 删项目留下孤儿文件 | 只删记录，`files/<项目id>/` 下的文件全留着 | 先删文件再删记录（顺序反了就永远找不回来） |
| 密码明文存储 | 字段名叫 `passwordHash`，存的实际是 `admin123` | scrypt + 16 字节随机盐；旧数据首次登录时自动静默升级 |
| 数据写入非原子 | `writeFileSync` 直接覆盖，写到一半崩溃整个文件报废 | 临时文件 + `fsync` + `rename` 原子替换 |
| 导入零校验 | 随便一个 JSON 都能导入，结构不对直接白屏 | 结构校验 + 预览统计 + 二次确认，且不覆盖本机账号 |
| 版本号可重复 | 同一项目下能建两个 `v1.0.0` | 提交前查重，输入时就提示 |
| CSV 导出半残 | 只导当前项目的版本，测试记录完全没有 | 含项目/芯片/客户/版本/文件信息，加 BOM 防 Excel 乱码 |
| 4 个 IPC 通道是死代码 | `openFile`/`saveDataPartial`/`getFileInfo`/`showConfirmDialog` 从未被调用 | 全部接上或移除 |
| 项目字段太少 | 只有名称和描述 | 加芯片型号、平台/框架、客户、项目状态 |

### 新增的能力

- **仪表盘**：项目总数、进行中数量、版本总数、测试总数；最近发布的版本；超过 30 天没测过的项目会亮黄灯提醒。
- **用户与权限**：管理员可增删改，只读用户只能看。密码用 scrypt 哈希，渲染进程永远拿不到哈希和盐。
- **版本对比**：任选两个版本并排看差异，变更的字段高亮。
- **自动备份**：每次保存前自动备份，保留最近 10 份；主文件损坏时自动从最近的可用备份恢复，坏文件另存隔离。
- **版本排序**：按语义化版本比较，`v1.10.0` 正确排在 `v1.9.0` 之后（纯字符串比较会出错）。

## v2.1：批量出货与设备级追溯

v2.0 解决的是「一个项目有哪些版本、测过几次」。但真正上产线后遇到的是另一个问题：**同一个项目出货几千台，每台的固件版本、系统环境、测试记录、故障状态都可能不同**。

v2.0 的模型装不下这个，因为测试记录直接挂在项目上，没有「设备」这个概念。v2.1 补上了。

### 三层实体

```
项目（产品型号）
  └─ 批次（一次投产，共用一套固件）
       └─ 设备（单台，用 SN 追溯）
```

关键设计：**设备的 `versionId` 和批次的 `versionId` 分开存**。产线经常出现「这批前 50 台烧 v2.1.0，后 150 台烧 v2.1.1」，设备级字段才能记录这种偏差，而这正是出问题时最常被追问的。

### 设备管理

- 每台设备记录：SN、所属批次、实际烧录固件、系统环境快照（OS/内核、rootfs、bootloader）、状态、测试记录
- 状态流转：待测 → 合格 / 不合格 / 返修中 → 已出货
- 支持按 SN、环境、备注搜索，按状态和批次筛选
- 勾选多台批量改状态（产线最常用）
- 每台设备可单独录入测试记录，区分**软件测试**与**硬件测试**

### 测试角色区分

软件测试和硬件测试关注的东西完全不同——前者看功能回归，后者看电压电流温度。混在一起统计没有意义，所以测试记录加了 `category` 字段：

| 角色 | 关心什么 | 对应功能 |
|---|---|---|
| 负责人 | 批次进度、问题收敛、出货决策 | 批次页、概览页 |
| 软件测试 | 这版固件在哪些设备上跑过、回归结果 | 设备页按固件筛选、软件测试记录 |
| 硬件测试 | 这台设备什么故障、返修到哪一步 | 设备页按 SN 查、问题单 |

### 问题单：批次性 vs 单机

这是我觉得最值得单独做的一块，因为两者处理方式完全不同：

| 类型 | 场景 | 处理方式 |
|---|---|---|
| **批次性问题** | 设计缺陷、器件选型错 | 一条记录覆盖整批，需要改设计或召回 |
| **单机问题** | 虚焊、静电击穿 | 只影响那一台，返修即可 |

如果不区分，就会出现「200 台各建一条相同的问题单」这种灾难。有了 `scope` 字段，一个问题单能关联整批，统计时也不会把批次性问题重复计 200 次。

### 增量 IPC：几千台设备也不卡

v2.0 每次保存都是整包来回传。实测 5000 台设备 × 5 条记录时：

| 环节 | 耗时 |
|---|---|
| 磁盘写入 | 4.2 ms |
| 备份复制 | 2.8 ms |
| **IPC 传输** | **33 ms** |
| **React 状态克隆** | **34 ms** |

磁盘不是瓶颈，IPC 和 React 才是。v2.1 把设备操作改成增量通道——只传动作、只回传受影响的项目：

```js
// v2.0：整包来回
saveData({ projects: [...全部项目...] })

// v2.1：只传动作
upsertDevices(projectId, devices)
addDeviceTestRecord(projectId, deviceId, record)
bulkAddDeviceTestRecords(projectId, rows)
```

实测 2000 台设备（0.88 MB）全量保存约 35 ms，增量操作只回传单台设备。

### 多人协作：合并导入而非覆盖

三个人各自一台电脑时，v2.0 的整包导入会把别人的数据冲掉。v2.1 改成按项目 id 合并：

- `mode=merge`（默认）：同 id 项目合并，双方独有的设备/记录都保留，同 id 记录取 `updatedAt` 较新的一方
- `mode=replace`：整包替换，需要显式指定

这样三个人各自录入的测试记录能汇到一起，而不是互相覆盖。

### CSV 批量导入

产线测试台导出的结果不会手敲。支持按 SN 匹配批量导入：

```csv
sn,testDate,tester,result,category,notes
EPM-0001,2026-11-03,张工,通过,hardware,电压正常
EPM-0002,2026-11-03,李工,失败,software,启动超时
```

匹配不到 SN 的行会被跳过并在结果中列出，不会静默丢弃。

### 修掉的一个静默丢数据缺陷

重构时发现 `normalizeData` 是白名单式重建——不在已知字段列表里的字段会被直接丢弃，而且不报错。实测确认：传入带 `devices` 的数据，保存后 `devices` 消失。

这意味着任何新增字段都会在保存时静默消失。v2.1 改成「保留未知字段、只规整已知字段」，并对项目、版本、设备、批次、问题单、测试记录六个层级都做了兜底。

## 功能一览

### 项目管理
- 项目基本信息：名称、描述、芯片型号、平台/框架、客户、状态（进行中 / 已完成 / 暂停 / 已归档）
- 项目卡片展示版本数、测试数、最新版本号、最近测试时间
- 支持按名称/描述/芯片/客户/平台全文搜索，按状态筛选

### 版本管理
- 每个版本可挂载：固件二进制文件、配置文件
- 自动计算并记录 MD5 和文件大小
- 变更说明支持多行
- 搜索、排序（生成时间 / 版本号 / 添加时间）、升降序切换
- 版本对比
- 版本号重复校验
- 点击文件名直接在文件管理器中定位

### 测试记录
- 月历视图，有记录的日期显示圆点（通过绿色、含失败红色）
- 记录字段：测试日期、测试人员、测试结果（通过/失败）、备注、关联版本
- 按日期查看当天所有记录
- 支持编辑和删除
- 月度统计：本月总测试次数、通过数、失败数

### 数据管理
- 导出 JSON 备份（含项目与用户角色，不含密码）
- 导出 CSV（给 Excel 用，已加 BOM）
- 导入 JSON 备份（结构校验 + 预览 + 二次确认）
- 自动备份与损坏恢复

## 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 运行时 | Electron 40 | 跨平台桌面应用 |
| 界面 | React 18 | 函数组件 + Hooks |
| 打包 | esbuild | 预编译，产物 205 KB |
| 存储 | 单 JSON 文件 | 无数据库，随时可拷走 |
| 密码 | Node.js `crypto.scryptSync` | N=16384, r=8, p=1，16 字节盐 |

没有引入 TypeScript、没有引入状态管理库、没有引入 UI 组件库。这是个单人维护的小工具，依赖越少活得越久。

## 快速开始

### 环境要求

- Node.js **18 及以上**（开发时用的是 v26）
- Linux / macOS / Windows

### 安装

```bash
git clone <repo-url>
cd embedded-project-manager
npm install
```

> **国内网络注意**：直连 npm 官方源和 GitHub 下载 Electron 二进制大概率会超时。建议先配好镜像：
>
> ```bash
> npm config set registry https://registry.npmmirror.com
> export ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/
> ```
>
> 如果 `npm install` 卡在 `electron postinstall`，可以单独补下载：
>
> ```bash
> node node_modules/electron/install.js
> ```

### 开发

```bash
npm start               # 构建渲染层 + 启动应用
npm run start:watch     # 监听模式，改渲染层代码自动重建（需手动重启应用）
npm run build:renderer  # 只重建渲染层
```

### 首次登录

应用首次启动会自动创建管理员账号：

| 用户名 | 密码 |
|---|---|
| `admin` | `admin123` |

**登录后请立刻在侧边栏点「改密」修改。** 这个初始密码是公开写在代码里的。

## 数据安全设计

这部分我花的时间最多，因为丢数据比功能少更难受。

### 原子写入

保存时不是直接覆盖 `data.json`，而是：

1. 写入同目录的临时文件 `.data.json.tmp-<pid>`
2. `fsync` 刷盘
3. `rename` 原子替换

`rename` 在同一文件系统内是原子操作，进程在任何时刻被杀都不会留下半个文件。

### 自动备份与恢复

- 每次保存**前**，先把当前 `data.json` 复制到 `backups/`
- 备份最多保留 10 份，超出的自动清理
- 启动时如果 `data.json` 解析失败：
  1. 把损坏文件复制为 `backups/corrupted-<时间戳>.json` 隔离
  2. 从最近的备份往前逐个尝试恢复
  3. 全部失败才重置为空数据，并在界面上明确提示

### 导入校验

导入的备份先经过 `validateImport`：

- 必须是 JSON 对象（数组、字符串直接拒绝）
- 必须有 `projects` 数组
- `users` 如果存在必须是对象
- 通过后规整 schema，补齐缺失字段、丢弃无法识别的字段
- 界面显示统计（多少项目、多少版本、多少测试记录）并二次确认
- **导入不覆盖本机账号表**，避免把自己锁在门外

### 权限边界

- 渲染进程只能拿到 `username` / `role` / `createdAt`，**密码哈希和盐永远不离开主进程**
- 渲染进程提交的补丁只包含 `projects` 和 `settings`，无法覆盖账号表
- 所有写操作在主进程侧再次校验管理员身份（不信任前端）
- 不能删除自己、不能撤销自己的管理员权限

### 路径穿越防护

所有文件操作都经过 `resolveStored`，把相对路径解析成绝对路径后检查是否仍在数据目录内。`../../etc/passwd` 这类路径会被直接拒绝。

## 从 v1.x 升级

**不需要做任何操作。** 直接覆盖安装即可：

- 旧版 `data.json` 会被自动识别并规整到新 schema
- 旧版项目补齐新字段（芯片型号等为空字符串）
- 旧版测试记录 `versionId` 为空，界面上显示「未关联版本」，可手动编辑补上
- 旧版明文密码在**首次登录时自动升级**为 scrypt 哈希，密码本身不变

升级前的数据会被自动备份，即使出问题也能回滚。

## 已知限制

老实写在这里，免得你踩坑：

1. **单机单用户**。数据存在本地，没有多机同步。多人协作请把备份文件放共享盘，各自导入。
2. **没有强制改密**。初始密码 `admin123` 是公开的，登录后需要自己改。如果给客户用，建议先改掉再交付。
3. **大文件没做分片**。固件直接整份复制到数据目录，几百 MB 的固件会占空间（但不会占内存，用的是流式复制）。
4. **没有撤销**。删除是硬删除，只有备份能救。删项目前会二次确认。
5. **导出 CSV 不含测试记录**。测试记录目前只在 JSON 备份里。
6. **Linux 下偶发白屏**。某些显卡驱动会导致 GPU 进程崩溃，可以设 `EPM_DISABLE_GPU=1` 启动应用禁用硬件加速。

## 常见问题

**Q：启动后界面空白？**
A：先看终端有没有报错。Linux 下如果是 GPU 问题，试 `EPM_DISABLE_GPU=1 npm start`。

**Q：忘记管理员密码了？**
A：编辑 `data.json`，把 `users` 里对应账号删掉，重启应用会自动补一个 `admin/admin123`。（前提是没有其他管理员账号）

**Q：能不能换个数据目录？**
A：目前跟随 Electron 的 `userData` 路径。想换位置可以把整个目录软链接过去。

**Q：`npm install` 一直超时？**
A：见上面「国内网络注意」。八成是 Electron 二进制下载卡住了。

**Q：打包时报 `Please specify project homepage`？**
A：deb 目标要求 `package.json` 有 `homepage` 字段，v2.0 已补上。如果你是改过 package.json 后出现，把它加回来即可。

## 开发约定

给自己定的规矩，也方便以后接手的人：

- **不引入不必要的依赖**。每加一个包都要问：能不能用 Node 内置模块解决？
- **日期一律用 `YYYY-MM-DD` 字符串存储**，需要计算时才转 `Date`，且必须用 `utils/date.js` 里的函数。
- **所有写操作走 `useAppData`**，不要在组件里直接调 `window.api`。数据一致性比少写几行代码重要。
- **主进程不信任渲染进程**。权限校验一律在主进程侧再做一次。
- **注释写「为什么」，不写「做什么」**。代码本身能说明做什么。
